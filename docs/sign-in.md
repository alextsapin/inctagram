# Вход в систему (Sign In)

Документ описывает бизнес-логику страницы входа (задача BLD-66): какие файлы
созданы, зачем каждый из них и почему он лежит именно в этом слое FSD.

Требования — ТЗ, UC-2 «Вход в систему». Контракт с бэкендом — Swagger
(`POST /api/v1/auth/login`, `GET /api/v1/auth/me`).

## Как работает вход

1. Пользователь заполняет форму и нажимает [ Sign In ].
2. `POST /api/v1/auth/login` с `{ email, password }`. Бэкенд возвращает
   `accessToken` в теле ответа и сам кладёт refresh-токен в httpOnly-cookie.
3. Access token сохраняем в памяти.
4. `GET /api/v1/auth/me` с заголовком `Authorization: Bearer <token>` — получаем
   `username`.
5. Переходим на страницу аккаунта `/profile/<username>`.

Если бэкенд ответил ошибкой, остаёмся на странице и показываем текст под полем
пароля.

## Структура файлов

```text
src/
├── shared/api/
│   ├── accessToken.ts        # хранение access token в памяти
│   ├── instance.ts           # axios instance для всех запросов к бэкенду
│   └── index.ts              # публичный API слоя
├── entities/session/
│   ├── api/api.ts            # getMe — запрос «кто я»
│   ├── model/types.ts        # тип Me
│   └── index.ts
└── features/sign-in/
    ├── api/api.ts            # signIn — запрос логина
    ├── model/types.ts        # SignInValues, LoginResponse
    ├── model/useSignIn.ts    # логика входа на useMutation
    ├── model/getSignInErrorText.ts  # текст ошибки по коду ответа
    └── ui/Form.tsx           # форма
```

Правило FSD, от которого зависит расположение файлов: слой может импортировать
только из слоёв **ниже** себя (`features` → `entities` → `shared`), а слайсы
одного слоя не импортируют друг друга.

## shared/api — запросы к бэкенду

Вход использует общие axios instance (`instance.ts`) и хранилище access token
(`accessToken.ts`). Это инфраструктура для всего проекта, а не только для
входа: зачем они нужны, как устроены и как настроить адрес бэкенда — в
[API: запросы к бэкенду](api.md).

## entities/session — текущий пользователь

Сущность «сессия» — это данные о том, кто сейчас вошёл в систему.

-   **Зачем `getMe` при входе.** В ответе `POST /api/v1/auth/login` есть только
    `accessToken`, а для перехода на `/profile/<username>` нужен `username`.
    Его возвращает `GET /api/v1/auth/me`.
-   **Почему отдельная сущность, а не файл внутри `features/sign-in`.** Текущий
    пользователь понадобится не только входу: шапке, выходу из системы (UC-4
    показывает email пользователя), защите страниц от неавторизованных. По FSD
    фичи не могут импортировать друг из друга, поэтому общие для нескольких
    фич данные выносятся в `entities`.
-   **Тип `Me`** повторяет `MeResponseDto` из Swagger: `userId`, `username`,
    `email`.

## features/sign-in — фича входа

Всё, что нужно только входу, лежит в слайсе фичи.

### api/api.ts

`signIn(values)` — `POST /api/v1/auth/login`. Лежит в фиче, потому что этот
запрос нужен только форме входа.

### model/types.ts

-   `SignInValues` — данные формы (`email`, `password`). Раньше тип был объявлен
    внутри `Form.tsx`; вынесен, потому что теперь он нужен ещё в `api` и в
    `useSignIn`.
-   `LoginResponse` — ответ логина (`accessToken`), по `LoginResponseDto` из
    Swagger.

### model/useSignIn.ts

Хук с логикой входа на `useMutation` из TanStack Query.

-   **Почему `useMutation`.** По правилам проекта
    ([TanStack Query](tanstack-query.md)) запросы, которые что-то меняют на
    сервере, делаются через `useMutation`. Вход создаёт сессию — это как раз
    такой запрос.
-   **Что даёт `useMutation` форме:** `mutate` — запустить вход, `isPending` —
    идёт ли запрос, `error` — ошибка последней попытки. Ни одного `useState`
    писать не пришлось.
-   **Шаги внутри:** логин → сохранить токен → `getMe` → переход на профиль.
    `useRouter` берётся из `next/navigation` (App Router), а не из
    `next/router`.

### model/getSignInErrorText.ts

Превращает ошибку запроса в текст для пользователя.

-   **Почему текст выбираем по коду ответа, а не берём из ответа сервера.** В
    Swagger у ответов с ошибками есть только описание для разработчиков, а тело
    ответа не описано. Тексты для пользователя берём из Figma и ТЗ, а сервер
    может формулировать иначе.
-   Коды вынесены в константы, потому что ESLint (`no-magic-numbers`) запрещает
    числа прямо в условиях.

| Ответ сервера                | Текст                                                 | Источник                 |
| ---------------------------- | ----------------------------------------------------- | ------------------------ |
| 400, 401                     | The email or password are incorrect. Try again please | Figma                    |
| 403 — email не подтверждён   | Your email is not confirmed. Please check your email  | временный, не согласован |
| 429 — слишком много попыток  | Too many attempts. Please try again later             | —                        |
| другое или сервер недоступен | Something went wrong. Please try again later          | —                        |

400 показываем так же, как 401: в Swagger у пароля при входе стоит
`minLength: 6`, и короткий пароль вернёт 400. Для пользователя это всё равно
«неверный пароль».

### ui/Form.tsx

-   **`mode: 'onTouched'`** — по ТЗ поле проверяется, когда пользователь из него
    ушёл. Режим `'onBlur'` не подходит: в нём `isValid` обновляется только при
    уходе с поля, и клик по кнопке сразу после ввода пароля попадал бы в ещё
    неактивную кнопку.
-   **Кнопка неактивна** (`disabled={!isValid || isPending}`), пока поля пустые
    или невалидные (ТЗ, UC-1 шаг 10) и пока идёт запрос — это заодно защищает
    от двойной отправки.
-   **Ошибка формата email** — текст из ТЗ:
    `The email must match the format example@example.com`. Текст
    «The email or password are incorrect» раньше стоял на этой проверке, но по
    смыслу это ответ сервера, поэтому он перенесён в `getSignInErrorText`.
-   **Пароль проверяется только на пустоту.** Длину и состав при входе не
    проверяем — так сказано в задаче бэкенда. Если правила пароля изменятся,
    форма входа не должна мешать войти пользователям со старыми паролями.

## Почему без Redux

Данные о пользователе приходят с сервера, а по правилам проекта серверные
данные живут в TanStack Query. Статус запроса (`isPending`, `error`) тоже даёт
TanStack Query. Если дублировать это в Redux, появятся два источника правды,
которые придётся синхронизировать вручную. Redux остаётся для клиентского
состояния интерфейса (модалки, уведомления и т. п.).

## Ограничения и что дальше

-   **После перезагрузки страницы нужно войти заново.** Access token хранится в
    памяти и пропадает при F5. Восстановление сессии через
    `POST /api/v1/auth/refresh` — отдельная задача.
-   Обновление access token через 15 минут (response interceptor для ответа
    401), защита страниц от неавторизованных и выход из системы — отдельные
    задачи.
-   Ответы 401/403/429 и переход в профиль будут проверены после деплоя
    бэкенда.
