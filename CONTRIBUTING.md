# Правила командной разработки Inctagram

Этот документ описывает именование веток и порядок внесения изменений в frontend-репозиторий Inctagram.

## 1. Основные ветки

- **`main`** — стабильная версия проекта. Изменения попадают через Pull Request после проверки. Создавать и объединять PR в `main` по правилам команды могут только `alextsapin` и `GromovaViktoriya` (авторство PR планируется дополнительно контролировать через GitHub Actions).
- **`develop`** — основная ветка командной разработки. Рабочие изменения поступают сюда через Pull Request и Code Review. У `alextsapin` есть исключение для прямого push; остальные участники работают через PR.

## 2. Именование рабочих веток

Формат:

```text
type/BLD-123-short-description
```

| Префикс | Когда использовать | Пример |
| --- | --- | --- |
| `feature/` | Новая функциональность | `feature/BLD-66-sign-in` |
| `fix/` | Исправление ошибки в разработке | `fix/BLD-105-login-error` |
| `refactor/` | Рефакторинг без изменения поведения | `refactor/BLD-110-auth-service` |
| `chore/` | Настройка проекта и обслуживание | `chore/BLD-115-eslint-config` |
| `docs/` | Документация | `docs/BLD-120-readme` |
| `test/` | Тесты | `test/BLD-125-auth-tests` |
| `hotfix/` | Срочное исправление стабильной версии | `hotfix/BLD-130-critical-auth-bug` |

Правила:

1. Используйте английские слова, латиницу и `kebab-case` (слова через дефис), без пробелов.
2. Указывайте номер задачи `BLD-123`, если задача есть в трекере. Для технических работ без номера допустимо, например, `chore/setup-ci`.
3. Кратко описывайте суть задачи; не включайте в название ветки имя разработчика, дату или номер спринта.
4. Одна ветка — одна задача или логически связанное изменение. Не используйте закрытую ветку для новой задачи.
5. Уже существующие ветки переименовывать не требуется. Стандарт применяется к новым веткам.

## 3. Откуда создавать ветки и куда открывать PR

- Для новой функциональности, обычных исправлений, тестов, документации и рефакторинга создавайте ветку **от `develop`**. PR направляйте **в `develop`**.
- **Hotfix:** любой разработчик может создать ветку `hotfix/*` **от `main`**, подготовить исправление и отправить её в GitHub. После этого нужно сообщить `alextsapin` или `GromovaViktoriya`. Один из них открывает PR из готовой `hotfix/*` **в `main`**, другой проверяет и одобряет изменения. После выпуска исправление переносится также в `develop`.
- Когда изменения в `develop` проверены и готовы к выпуску, **`alextsapin` или `GromovaViktoriya`** создаёт отдельный **release PR: `develop` → `main`**. Другой ответственный одобряет PR.

## 4. Code Review и слияние

- Перед слиянием PR требуется как минимум одно одобрение от Code Owner: **`@alextsapin` или `@GromovaViktoriya`**.
- Автор не может одобрить собственный PR. Если PR создал один из Code Owners, его одобряет другой.
- После новых коммитов прежнее одобрение сбрасывается; все обсуждения должны быть разрешены перед слиянием.
- В **`develop`** Merge после выполнения правил может делать любой участник с правом записи в репозиторий.
- **Создавать PR в `main`** (включая release и hotfix) по регламенту могут только `alextsapin` и `GromovaViktoriya`. Остальные разработчики создают PR в `develop`, а для hotfix передают готовую ветку ответственным.
- В **`main`** Merge разрешён только `alextsapin` и `GromovaViktoriya` при выполнении требований Code Review. Сейчас это ограничено GitHub Rulesets; запрет слияния PR от других авторов будет дополнительно реализован через GitHub Actions и обязательную CI-проверку.
- В `develop` для `alextsapin` предусмотрено административное исключение на прямой push; для обычных задач рекомендуется использовать PR.

## 5. Перед открытием PR

- Убедитесь, что изменения относятся к заявленной задаче и не содержат случайных файлов.
- Проверьте доступные локальные проверки проекта (например, линтер, типы, сборку).
- Укажите номер задачи, краткое описание изменений и способ проверки в тексте PR.
- Назначьте ответственного на Code Review.

> Правила обязательных автоматических CI-проверок будут добавлены после настройки CI.
